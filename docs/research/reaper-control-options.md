## 1. Natywne rozszerzenie C++ (`reaper_*.dll`)

**Entry point.** Rozszerzenie musi eksportować `int ReaperPluginEntry(HINSTANCE hInstance, reaper_plugin_info_t *rec)`; zwraca 1 jeśli kompatybilne, `rec == NULL` oznacza unload (`RP:133-136`, makro `REAPER_PLUGIN_ENTRYPOINT` `RP:56`, eksport `__declspec(dllexport)` na Windows `RP:45`). `rec` zawiera `caller_version` (`REAPER_PLUGIN_VERSION 0x20E`), `hwnd_main`, `Register()` i `GetFunc()` (`RP:151-161`, `RP:348`). Przykład produkcyjny: ReaPack sprawdza `caller_version`, ładuje API i rejestruje hooki (`REAPACK src/main.cpp:126-148`).

**Import funkcji API.** Funkcje pobiera się dynamicznie przez `rec->GetFunc("NazwaFunkcji")`; nie wolno zakładać, że funkcja istnieje (`RPF:29-37`). Wygodny wariant: w jednym pliku `#define REAPERAPI_IMPLEMENT` przed `#include "reaper_plugin_functions.h"`, potem `REAPERAPI_LoadAPI(rec->GetFunc)` w entry poincie (0 = sukces); opcjonalnie `REAPERAPI_MINIMAL` + `REAPERAPI_WANT_<funkcja>` (`RPF:39-47`).

**Build na Windows.** Cockos: rozszerzenia na win32 pisze się w C++ i kompiluje **MSVC** (wymagane ABI MSVC dla pure-virtual interfejsów, MinGW nie działa) (`SDKPAGE`, sekcja „Development”; też `RPF:27`). Do kompilacji przykładów SDK trzeba dołączyć WDL (`README` repo SDK). CMake nie jest wymagany przez Cockos, ale np. ReaPack używa CMake ≥ 3.15 + C++17/MSVC + vcpkg (`REAPACK README.md:23-24, 47-62`).

**Wiele platform?** Nie — DLL jest binarką per OS/arch. Na Windows wystarczy build x64. macOS/Linux wymagałyby osobnych buildów z SWELL (`RP:42-54`: gałąź `#else` dołącza `swell.h`, `RP:49`). Dla jednego laptopa z Windows: jeden build x64.

**Wątki.** SDK nie zawiera ogólnej reguły „API tylko z main thread” w jednym miejscu, ale:
- pojedyncze funkcje są jawnie oznaczone jako „threadsafe” (`Audio_IsRunning`, `Audio_IsPreBuffer` `RPF:249-257`; `kbd_OnMidiEvent`/`kbd_OnMidiList` „can be called from anywhere (threadsafe)” `RPF:4180-4188`), a inne jako „Must only call from the main thread” (`RPF:549, 557, 1083`) — co implikuje, że domyślnie API **nie** jest thread-safe;
- dojrzałe rozszerzenia zawsze przerzucają pracę na main thread: ReaPack — kolejka z mutexem opróżniana przez `plugin_register("timer", ...)` (`REAPACK src/event.cpp:24-62`); ReaLearn — middleware „A Tower layer that will cause wrapped services to be executed in REAPER's main thread” dla serwera HTTP (`HELGO main/src/infrastructure/server/layers/main_thread.rs:8-59`).
- Twierdzenie „żadnej funkcji poza oznaczonymi nie wolno wołać z innego wątku” jako oficjalna reguła Cockos: **niezweryfikowane** w dokumentacji pierwotnej (jest to jednak praktyka wynikająca z powyższego).

**Mechanizmy marshalingu na main thread:**
- `Register("timer", void(*)())` — funkcja wołana cyklicznie (`RP:247-249`); wzorzec: wątek sieciowy wrzuca zadania do kolejki pod mutexem, timer je wykonuje (ReaPack, j.w.).
- `IReaperControlSurface::Run()` — „called 30x/sec or so” (`RP:1482`); powierzchnię można dodać „behind the scenes” przez `Register("csurf_inst", instance)` (`RP:1544`). Wbudowany web remote robi dokładnie to: cały serwer HTTP (jnetlib, nieblokujący) obsługiwany jest w `Run()` → `serv.run()` (`WWW:928-934`), czyli na main thread, bez osobnego wątku.

Biblioteki (zweryfikowane tylko cechy z ich repozytoriów, nie użycie w rozszerzeniach REAPER-a):

- **mongoose** — dual GPLv2/komercyjna (`LICENSE` l.5-8) → licencyjnie kłopotliwa.

## 4. Wbudowany web remote (opcja a)

**Protokół** (`MJS:30-48`): `GET /_/CMD;CMD;CMD` — wiele komend w jednym requeście, odpowiedź `text/plain`, linie `\n`, pola `\t` (`WWW:678-708`).

| Potrzeba | Komenda | Źródło |
|---|---|---|
| Lista ścieżek | `NTRACK`; `TRACK` / `TRACK/i` / `TRACK/a-b` → `TRACK \t idx \t name \t flags \t vol \t pan \t peak \t ... \t sendcnt \t recvcnt \t hwoutcnt \t color` (0 = master; taby/nowe linie w nazwie zamieniane na spację `WWW:537-541`) | `MJS:73-104` |
| Odczyt send/receive | `GET/TRACK/x/SEND/y` → `SEND \t x \t y \t flags \t vol \t pan \t other_track_index`; **y = -1 pierwszy receive, -2 drugi…**; `flags&8` = mute. Dla y≥0 indeksy obejmują najpierw HW outputs, potem sendy (`WWW:405-421`) | `MJS:106-116` |
| Ustawienie głośności | `SET/TRACK/x/SEND/y/VOL/v` (1.0 = 0 dB; sufiks `e` = koniec gestu, `E` = instant edit), realizowane przez `SetTrackSendUIVol` | `MJS:204-208`, `WWW:329-333` |
| Mute send | `SET/TRACK/x/SEND/y/MUTE/v` (-1 toggle) | `MJS:198-202` |
| Akcje | sama liczba (np. `40364`) lub `_NAZWA` (registered command) | `MJS:50-54`, `WWW:215-220` |
| Stan toggle (metronom) | `GET/40364` → `CMDSTATE \t 40364 \t state` | `MJS:269-277` |
| Transport | `TRANSPORT`, `BEATPOS`, `SET/POS/…` | `MJS:56-71, 216-225` |
| Most do OSC | `OSC/oscstring[:val]` | `MJS:280-282` |
| Stan współdzielony | `GET/SET/EXTSTATE`, `PROJEXTSTATE` | `MJS:237-267` |

Konwersja dB: `mkvolstr` liczy `ln(v)*8.6858…` (`MJS:395-400`).

**Push?** Nie. Tylko request/response HTTP; oficjalny klient robi polling (`wwr_req_recur`, timer 100 ms, `MJS:5-10, 323-379`). W `csurf_www.cpp` brak WebSocket/SSE (brak `Upgrade`/`websocket` w źródle).

**Pliki statyczne.** Dowolny plik z `%APPDATA%\REAPER\reaper_www_root` (user root, tworzony automatycznie `WWW:100-110`), fallback do katalogu programu (`WWW:112-124`, `WWW:714-745`); podkatalogi działają (ścieżka doklejana wprost, blokowane `..`). Bez rozszerzenia próbuje `.html`. Zastrzeżenia dla Flutter Web:
- MIME znane tylko dla jpg/png/gif/txt/htm(l)/js/css/xml/svg; reszta, w tym **`.wasm` i `.json`, idzie jako `application/octet-stream`** (`JNL webserver.h:203-221`). `WebAssembly.instantiateStreaming` wymaga `application/wasm` — czy Flutter Web (CanvasKit/skwasm) ma fallback: **niezweryfikowane**.
- Pliki inne niż html/js/css dostają `Expires` +3600 s (`WWW:15, 756-768`).
- Obsługa query stringów (`?v=…`) przy plikach statycznych — niezweryfikowane.

**Konfiguracja** (Preferences → Control/OSC/web): port domyślnie **8080** (`WWW:881-883`), opcjonalny login `user:pass` → HTTP **Basic auth** (`WWW:652-673`), strona domyślna (`WWW:863-864`), opcjonalny „rc.reaper.fm” lookup (`WWW:885-895`).

**Ograniczenia:**
- **CORS**: brak domyślnie; można dodać nagłówki w `reaper.ini`, sekcja `[csurf_www]`, klucze `header1`…`header32` (np. `header1=Access-Control-Allow-Origin: *`) — stosowane **tylko do odpowiedzi `/_/`** (`WWW:630-636, 704-705`). Dla natywnej apki Flutter (Android/iOS) CORS nie ma znaczenia.
- Brak HTTPS (jnetlib, brak TLS w kodzie) — w sieci lokalnej akceptowalne.
- Rate limiting: nie znalazłem w kodzie (niezweryfikowane jako brak). Limit połączeń w `WebServerBaseClass` domyślnie 100 (`JNL webserver.cpp:27`); czy `csurf_www` go zmienia — niezweryfikowane.
- Requesty obsługiwane ~30×/s w `Run()` (`RP:1482`), więc dodatkowe opóźnienie do ~33 ms.
- Adresowanie wyłącznie po **indeksie** ścieżki/receive'a — po dodaniu/przesunięciu ścieżek indeksy się zmieniają; trzeba odświeżać `TRACK` i weryfikować nazwę.

## 5. OSC (opcja d)

Domyślny `Default.ReaperOSC` zawiera:
- `TRACK_NAME s/track/@/name` (`ROSC:295`),
- `TRACK_SEND_VOLUME n/track/@/send/@/volume` + `s/.../volume/str` (`ROSC:316-317`),
- `TRACK_RECV_VOLUME n/track/@/recv/@/volume` + `/str`, `TRACK_RECV_NAME` (`ROSC:321-323`),
- `METRONOME t/click` (`ROSC:147-150, 230`), `ACTION i/action t/action/@` (`ROSC:466`).

Plus: REAPER **wysyła feedback (push)** — w `csurf_osc.cpp` obsługa `CSURF_EXT_SETSENDVOLUME/SETRECVVOLUME` i metronomu (`OSCC:2704-2709, 3171-3189, 3301`).

Ograniczenia:
- `@` dla ścieżki jest **względny wobec banku**; `DEVICE_TRACK_COUNT 8`, `DEVICE_SEND_COUNT 4`, `DEVICE_RECEIVE_COUNT 4` (`ROSC:30-32, 183-187`) — trzeba edytować kopię pliku lub wysyłać `/device/...count` (`ROSC:477-479`).
- `n` = pozycja fadera znormalizowana wg preferencji fadera, nie liniowe gain (`ROSC:101-112`); dla sendów brak wariantu `f/.../db` w domyślnym pliku (`ROSC:316-325`).
- Domyślny config generuje dużo feedbacku (VU, czas) — zaleca się wycięcie (`ROSC:191-194`).
- UDP; adres docelowy feedbacku i liczba instancji (czy każdy telefon potrzebuje osobnej instancji control surface) — **niezweryfikowane** w źródle.

## 6. ReaScript Lua (opcja c)

- Lua 5.4 jest wbudowane (`RSPAGE`, sekcja „Lua (v5.4)”); dokumentacja nie wymienia żadnego API socketów — **brak natywnych socketów** (wniosek z braku w `RSPAGE`; pełnej listy funkcji ReaScript nie przeglądałem).
- Długo działające skrypty działają przez `reaper.defer()` (cykliczne wywołanie na main thread, `RSPAGE` „Deferred scripts”), więc serwer musiałby być nieblokujący i pompowany z `defer`.
- Biblioteka zewnętrzna: `mavriq-dev/mavriq-lua-sockets` — „Static Builds of lua-sockets for use in Reaper”, ostatni push 2023-11-19 (GitHub API). Wsparcie WebSocket/serwera — niezweryfikowane. Natywne DLL ładowane przez `require` = ten sam problem dystrybucji co rozszerzenie, a mniej kontroli.

## Rekomendacja

**v1: (a) wbudowany web remote + natywna aplikacja Flutter (Android/iOS)** wołająca `http://<laptop>:8080/_/...`. Wszystko, czego v1 potrzebuje, jest w API: `TRACK` (znajdź ścieżki z prefiksem „Odsłuch:” i ich `recvcnt`), `GET/TRACK/x/SEND/-k` (głośność + `other_track_index` źródła), `SET/TRACK/x/SEND/-k/VOL/v`, `40364`/`GET/40364`. Zero kodu po stronie REAPER-a, wykonanie na main thread gwarantowane przez REAPER. Polling 200–500 ms z batchowaniem komend w jednym requeście w zupełności wystarczy dla kilku muzyków. Hostowania Flutter Web z `reaper_www_root` nie polecam ze względu na MIME `.wasm` (niezweryfikowany fallback).

**Upgrade do (b)** gdy: potrzebny push/niska latencja dla wielu klientów, mierniki (meters) per send, stabilne ID (GUID) zamiast indeksów, autoryzacja per muzyk lub logika serwerowa (np. „mój mix”). Wzorzec: wzorować się na `csurf_www.cpp` (serwer w `Run()` via `csurf_inst`) albo wątek sieciowy (cpp-httplib/IXWebSocket) + kolejka opróżniana przez `timer`, zmiany pushowane z `IReaperControlSurface::Extended(CSURF_EXT_SETRECVVOLUME…)`. Zaprojektuj protokół apki tak, by warstwę transportu dało się podmienić.

OSC (d) traktuję jako plan B na push bez pisania C++, ale bankowanie i znormalizowana skala fadera komplikują aplikację. Lua (c) — odradzam.
